## ⚠️ High-Priority (머지 전 처리 권장)

### D-1. 포커스 인디케이터가 밝은 배경에서 1.22:1입니다

```css
button:focus-visible, a:focus-visible, input:focus-visible { outline:3px solid #ffd84d; outline-offset:3px }
```

측정값(계산 + 실제 렌더 캡처 확인):

| 배경 | 대비 | WCAG 1.4.11 기준 | 판정 |
|---|---|---|---|
| `--paper` `#f3f1e9` (헤더·내비·본문 대부분) | **1.22 : 1** | 3 : 1 | ❌ |
| `--navy` `#071a2d` (히어로 우측·푸터) | 약 8.9 : 1 | 3 : 1 | ✅ |

앱 면적의 대부분이 페이퍼 배경이므로, **키보드 사용자가 실제로 마주치는 포커스 표시의 대부분이 기준 미달**입니다. Tab으로 내비를 이동하는 캡처에서도 노란 테두리가 배경에 묻힙니다.

노란색을 유지하려면 어두운 테두리를 겹쳐 이중 링(예: 바깥 `--navy` 1px + 안쪽 노랑 3px)으로 만들거나, 밝은 표면에서만 `--navy` 계열로 전환하는 방식이 안전합니다.

**Phase 4 · WCAG 2.1 AA 1.4.11 Non-text Contrast**

### D-2. 모달을 열어도 포커스가 모달로 가지 않고, 갇히지도 않습니다

로그인 모달을 열고 Tab을 **14번** 눌러 활성 요소를 추적했습니다.

```
모달 오픈 직후 activeElement : BODY            ← 포커스 미이동
Tab  1  → A.brand      "경충FC 홈"      inModal: false
Tab  2  → A.active     "홈"            inModal: false
Tab  3~9 → 내비 링크 7개                inModal: false
Tab 10  → A.youtube-link                inModal: false
Tab 11  → BUTTON.login-button           inModal: false
Tab 12  → BUTTON.cta   "다음 일정 참석하기" inModal: false
Tab 13  → BUTTON.text-link              inModal: false
Tab 14  → BUTTON       "전체 일정 보기"   inModal: false
```

**14번 모두 모달 바깥입니다.** 게다가 `.login-modal`에는 `aria-modal="true"`가 선언돼 있어 스크린리더는 배경 콘텐츠를 숨깁니다. 즉 **키보드 포커스는 스크린리더가 존재하지 않는다고 알린 요소들 위를 순회**합니다. 선언만 있고 구현이 없을 때 오히려 더 나빠지는 전형적인 경우입니다.

추가로 확인된 동작 불일치:

| 동작 | 로그인 모달 | 모바일 메뉴 |
|---|---|---|
| Escape로 닫기 | ❌ 닫히지 않음 | ✅ 닫힘 |
| 배경 클릭으로 닫기 | ✅ 닫힘 | — |
| 열 때 포커스 이동 | ❌ BODY에 잔류 | ✅ 첫 항목으로 이동 |

모바일 메뉴는 이미 올바르게 구현돼 있으므로, 그 패턴을 모달에 옮기면 됩니다. 대상은 `role="dialog"`를 쓰는 4곳 전부입니다 — `로그인 또는 회원가입`, `가입 이메일 등록`, `경충FC 가입 신청`, `MOM 투표`.

> 참고: `aria-label`은 4개 모달 모두 올바르게 붙어 있습니다. 이름 부여는 문제없고, **포커스 관리만** 빠져 있습니다.

**Phase 1 · Phase 4 · WCAG 2.1 AA 2.4.3 Focus Order**

### D-3. 브랜드 그린을 텍스트로 쓰면 전부 대비 미달입니다

`--green: #35a853`을 글자색으로 사용하는 지점의 실측값:

| 위치 | 크기 / 굵기 | 배경 | 실측 | 필요 | 판정 |
|---|---|---|---|---|---|
| 히어로 `<em>우리의 풋살.</em>` | 64px / 950 | `#f3f1e9` | **2.70** | 3.0 (큰 텍스트) | ❌ |
| `UPCOMING SCHEDULE` 등 eyebrow | 9px / 900 | `#f3f1e9` | **2.70** | 4.5 | ❌ |
| `의사 결정 투표 · 진행 중` | 10px / 900 | `#ffffff` | **3.05** | 4.5 | ❌ |
| `회원 설문 · 진행 중` | 10px / 900 | `#ffffff` | **3.05** | 4.5 | ❌ |

히어로 문구는 큰 텍스트 완화 기준(3:1)에도 못 미칩니다. 브랜드 아이덴티티의 핵심 색이라 **색을 바꾸는 것보다, 텍스트용 그린을 따로 두는 편**이 현실적입니다. 배경·테두리·강조 블록에는 지금의 `#35a853`을 그대로 쓰고, 글자에는 어둡게 조정한 토큰(예: `--green-text`)을 쓰는 분리입니다. 실제로 `.event-card.past`에서는 이미 `#187435`(약 6.5:1)를 쓰고 있으니, 그 값이 그대로 후보가 됩니다.

**Phase 3 · Phase 4 · WCAG 2.1 AA 1.4.3 Contrast**

### D-4. `/events` 카드가 375px에서 그리드가 어긋납니다

`.event-card`는 자식이 **3개**(`event-date` / `event-info` / `event-action`)인데, 모바일 선언은 **2열**입니다.

```css
.event-card{grid-template-columns:140px 1fr auto}              /* 데스크톱: 3열 */
@media(max-width:900px){ .event-card{grid-template-columns:80px 1fr} }  /* 모바일: 2열 */
```

375px에서 실측한 결과:

```
cardCols : "80px 221.5px"    cardRows : "179px 82px"   ← 2×2 그리드로 접힘
  event-date    x=40  y=476  80×87    ← 1행 높이 179px 안에서 세로 가운데 정렬
  event-info    x=120 y=389  222×179
  event-action  x=120 y=568  222×82   ← 2열로 밀려나 왼쪽 80px 빈 여백
```

화면에 나타나는 증상은 두 가지입니다.

1. **날짜 블록이 제목에서 떨어집니다.** `08 토요일`(y=476)이 제목 `주말 정기 풋살`(y=414)이 아니라 장소 줄 옆에 놓입니다. 날짜와 제목이 시각적으로 연결되지 않습니다.
2. **액션 영역 왼쪽에 80px 빈 열이 생깁니다.** `회원 0명 · 용병 0명`과 버튼이 x=120에서 시작해, 좁은 화면에서 가장 아까운 가로 폭을 그대로 버립니다.

또한 같은 카드의 `<p>`가 `display:flex`인 상태로 `구장 확정 후 안내 · 18:00`을 담고 있어, 장소명이 두 줄로 접히면 **가운뎃점(·)이 오른쪽 끝에 홀로 남습니다.**

모바일에서는 2열 그리드를 유지하되 `event-action`을 `grid-column:1/-1`로 펼치거나, 카드 전체를 세로 스택으로 바꾸는 것이 자연스럽습니다.

**Phase 2 · Phase 3**

### D-5. 되돌릴 수 없는 동작의 체크박스가 13×13px입니다

`/feedback`의 체크박스 두 개를 모든 뷰포트에서 실측했습니다.

```
INPUT (목록에서 익명으로 표시)      13 × 13 px
INPUT (공개 GitHub 이슈로도 등록)   13 × 13 px
INPUT (제목 입력)                  282 × 43 px   ← 44px에서 1px 부족
```

브라우저 기본 크기 그대로입니다. WCAG 2.2 AA(2.5.8 Target Size Minimum)의 24×24px에 못 미치고, 모바일 권장치 44×44px의 **1/3도 되지 않습니다.**

문제가 더 큰 이유는 **이 중 하나가 공개 GitHub 저장소에 제목과 본문을 영구 게시하는 스위치**라는 점입니다. 앱에서 가장 되돌리기 어려운 동작이 가장 누르기 어렵고, 동시에 **가장 잘못 눌리기 쉬운** 컨트롤에 걸려 있습니다.

`<label>`이 감싸고 있어 라벨 텍스트를 눌러도 토글되지만, 라벨 영역 자체의 높이도 44px 미만입니다. 체크박스를 `width/height:20px` 이상으로 키우고 라벨 행에 `min-height:44px`를 주면 두 문제가 함께 해결됩니다.

**Phase 2 · Phase 4 · WCAG 2.2 AA 2.5.8**

## 📋 Medium-Priority (후속 PR 권장)

### D-6. 로그아웃 상태에서 폼이 전부 열려 있습니다

`/feedback` 실측:

```
submit  : "의견 접수"  disabled = true
category: ENABLED   title: ENABLED   body: ENABLED
is_anonymous: ENABLED   publish_to_github: ENABLED
```

제출 버튼만 잠겨 있고 입력은 전부 가능합니다. 상단에 `로그인하고 의견 남기기` 버튼이 있지만 그 아래 폼이 정상으로 보이므로, 사용자는 **5,000자를 다 쓰고 나서야** 낼 수 없다는 것을 압니다. 작성 내용도 보존되지 않습니다.

폼 전체를 `fieldset disabled`로 잠그고 사유를 상단에 두거나, 입력을 허용하려면 최소한 `localStorage` 임시 저장이 필요합니다.

### D-7. 글자 수 카운터가 없는데 입력이 조용히 잘립니다

```
title : maxlength=120     body : maxlength=5000     카운터 UI: 0개
```

`maxlength`는 초과 입력을 **아무 피드백 없이 무시**합니다. 5,000자 근처에서 타이핑이 멈추면 사용자는 앱이 멈춘 것으로 읽습니다. `1,240 / 5,000` 형태의 카운터를 두고 임계치 근처에서 색을 바꾸는 정도면 충분합니다.

### D-8. GitHub 공개 안내가 체크박스 *뒤*에 있습니다

DOM 순서를 실측한 결과 `checkbox-before-notice`입니다. 즉 `공개 GitHub 이슈로도 등록`을 체크한 **다음**에 `선택하면 제목과 내용이 공개 저장소에 게시됩니다`를 읽게 됩니다. 결정에 필요한 정보는 결정 전에 있어야 합니다.

### D-9. 토스트 라이브 리전이 메시지와 동시에 DOM에 삽입됩니다

```tsx
{toast && <div className={`toast ${toast.kind}`} role={toast.kind === "error" ? "alert" : "status"}>…</div>}
```

`role`은 올바르게 붙었지만(이번 작업분의 개선), **컨테이너와 내용이 같은 순간에 나타납니다.** 비어 있는 라이브 리전이 먼저 존재하고 나중에 내용이 채워져야 안정적으로 낭독되며, 동시 삽입은 NVDA·VoiceOver에서 누락되는 사례가 알려져 있습니다.

빈 `<div role="status">` / `<div role="alert">`를 상시 렌더해 두고 메시지 텍스트만 갈아끼우면 해결됩니다. 8개 라우트 전부에서 평상시 라이브 리전이 **0개**로 측정된 것도 이 구조 때문입니다.

### D-10. `prefers-reduced-motion`이 transition만 끄고 animation은 놓칩니다

```css
@media(prefers-reduced-motion:reduce){ *{ scroll-behavior:auto!important; transition:none!important } }
```

이번에 추가된 스켈레톤은 `transition`이 아니라 `animation: loading-shimmer 1.2s infinite`입니다. 현재 규칙으로는 **감속 모션 설정을 켠 사용자에게도 계속 반짝입니다.** 페이지 로딩마다 반복되는 애니메이션이라 체감이 큽니다. `animation:none!important`를 같은 블록에 추가하면 됩니다(스켈레톤은 정지 상태로도 기능합니다).

### D-11. 날짜 표기가 두 가지입니다

| 화면 | 출력 | 사용 함수 |
|---|---|---|
| 공지 목록 | `2026. 8. 9.` | `toLocaleDateString("ko-KR")` |
| 일정 등 | `2026년 8월 9일 토` | `formatDate()` |

같은 앱 안에서 형식이 갈립니다. `formatDate()`가 이미 있으므로 공지 목록도 그쪽으로 통일하면 됩니다.

### D-12. 로그인 게이트 화면이 1440px에서 60% 이상 비어 있습니다

`/fees`, `/rankings`는 제목·설명·버튼이 상단 450px 안에 끝나고 그 아래 푸터까지 빈 화면입니다. 버튼 하나가 좌측에 덩그러니 놓인 형태라 "로드 실패"처럼 읽힐 여지가 있습니다. 다른 화면의 `Empty` 컴포넌트(아이콘 + 제목 + 설명 중앙 정렬)를 재사용하면 같은 상태가 의도된 화면으로 보입니다. **회비 정책처럼 가입 검토자에게 공개해도 되는 정보**를 이 자리에 두는 것도 방법입니다.

### D-13. 헤더가 `position: relative`입니다

실측값 `relative`. 스크롤하면 내비가 화면에서 사라지므로, 목록이 길어지는 화면(공지·일정·회비)에서 탭을 옮기려면 매번 최상단으로 돌아가야 합니다. 모바일에서 특히 부담이 큽니다.

### D-14. 빈 상태 CTA만 44px 규칙에서 빠졌습니다

```
"전체 일정 보기" 버튼 : 94 × 30 px
```

`globals.css`에 `.schedule-foot button{min-width:44px;min-height:44px}`가 있지만, 이 버튼은 `.schedule-empty` 안에 있어 선택자에 걸리지 않습니다. 규칙이 **클래스 위치에 의존**하고 있어 새 상태를 추가할 때마다 빠질 수 있습니다. 선택자를 상태 컨테이너 기준(`.schedule-card button`)으로 올리는 편이 안전합니다.

### D-15. 9~11px 텍스트가 페이지마다 5~14개입니다

측정치: 홈 14개, 의견 8개, 공지·일정·참여 각 7개, 회원·회비·랭킹 각 5개.

대부분 `.eyebrow`(11px)와 `<small>` 오버라인(9~10px)입니다. `letter-spacing`이 1.6~2.5px로 넓어 가독성이 더 떨어집니다. 장식 요소지만 `UPCOMING SCHEDULE`, `NEXT SCHEDULE RSVP`처럼 **정보를 담은 라벨**도 9px로 렌더됩니다. 정보성 라벨은 12px 이상으로 올리고, 순수 장식은 개수를 줄이는 편이 낫습니다(→ 기존 문서 S-8과 같은 결론).

## 검증 한계

이 문서가 **다루지 않은** 범위를 분명히 해 둡니다.

- **로그인 후 화면과 운영진 콘솔은 라이브 검증하지 않았습니다.** 계정 인증이 필요한데 저는 자격 증명을 입력하지 않습니다. RSVP 실행, 회비 표, 랭킹, 출석 체크, 권한 매트릭스, 설문 편집기는 이번 실측에 포함되지 않았습니다 — 해당 영역은 `docs/ui-ux-review.md`의 코드 기반 분석을 참고하세요.
- **로그인 모달의 포커스 문제(D-2)는 나머지 3개 모달에도 동일하게 적용된다고 판단했습니다.** 직접 실행한 것은 로그인 모달 한 곳이고, 나머지는 같은 마크업 패턴(`role="dialog" aria-modal="true"` + 포커스 이동 코드 없음)을 근거로 한 추론입니다.
- **명암비는 계산값입니다.** 실제 렌더 픽셀에서 전경/배경 색을 읽어 WCAG 공식으로 계산했고, 반투명 레이어가 겹친 지점에서는 오차가 있을 수 있습니다.
- 초기 검토에서 375px 가로 잘림을 의심했으나, **Chrome의 최소 창 너비로 인한 캡처 아티팩트**였습니다. 기기 메트릭을 직접 지정해 재측정한 결과 실제 가로 스크롤은 없습니다.
