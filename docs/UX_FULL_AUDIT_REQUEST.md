# 경충FC 클럽하우스 사용자 경험 전수점검 요청

현재 프로젝트를 실제 사용자의 관점에서 전수점검해 주세요.

## 1. 점검 목적

이번 점검의 최우선 목표는 코드 구조나 기술 품질 평가가 아닙니다.

사용자가 다음을 얼마나 쉽고 명확하게 수행할 수 있는지 검증하세요.

- 원하는 기능을 빠르게 발견할 수 있는가
- 현재 상태와 다음 행동을 즉시 이해할 수 있는가
- 적은 클릭·입력·스크롤로 핵심 과업을 완료할 수 있는가
- 성공, 실패, 처리 중, 권한 제한 상태를 분명히 알 수 있는가
- 실수하거나 실패했을 때 쉽게 복구할 수 있는가
- 모바일과 키보드 환경에서도 불편 없이 사용할 수 있는가

코드·보안·성능 문제는 사용자에게 행동 실패, 잘못된 정보, 입력 유실, 권한 혼란, 지연 또는 접근성 차단을 일으킬 때만 보고하세요.

“예쁘지 않다”, “더 현대적으로 만들 수 있다” 같은 취향 평가는 제외하고, 사용자의 놓침·오해·실수·과업 지연으로 이어지는 문제만 결함으로 분류하세요.

## 2. 시작 전 필수 사항

1. `C:\Users\jaywa\.ai\rules\`의 모든 `.md` 파일과 프로젝트의 `AGENTS.md`, `CLAUDE.md`를 먼저 읽고 준수하세요.
2. 현재 브랜치, HEAD SHA, 작업 트리 상태, 실행 대상 URL을 기록하세요.

5. 로컬 실행 전에 Supabase 연결 대상이 격리된 테스트 환경인지 시크릿을 출력하지 않고 확인하세요. `.env.local`이 운영 프로젝트를 가리키거나 대상을 안전하게 판별할 수 없으면 인증 화면, `/feedback`, Edge Function 호출처럼 열람만으로도 외부 동기화나 쓰기가 발생할 수 있는 경로를 실행하지 마세요.
6. 안전한 격리 환경이 확인된 경우에만 `npm run dev`로 로컬 앱을 실행하고 브라우저에서 직접 확인하세요. 그렇지 않으면 설정된 운영 URL `https://gyungchung.vercel.app`에서 부작용 없는 공개 GET 화면만 확인하고 제약을 보고하세요.
7. 네트워크 요청 차단이나 mock이 없는 운영 연결 상태에서 임의로 장애를 주입하지 마세요.
8. `lint`나 `build` 통과, 콘솔 오류 부재를 UX 통과 근거로 사용하지 마세요.

## 3. 변경 및 운영 안전 경계

이번 작업은 기본적으로 읽기 전용입니다.

금지 사항:

- 코드·설정·문서 수정
- 커밋, push, PR, 배포
- 운영 DB 쓰기 또는 마이그레이션
- 계정·역할·권한 변경
- 운영 환경에서 RSVP, 회비, 출석, 투표, 설문, 의견 제출
- GitHub 이슈 생성·수정·종료
- 실제 회원 개인정보나 시크릿의 출력·캡처·보고서 첨부
- `.env.local`, 토큰, 키 등 시크릿 내용 전송

쓰기 작업이 필요한 흐름은 명시적으로 제공된 격리 테스트 환경과 폐기 가능한 테스트 데이터가 있을 때만 수행하세요. 그렇지 않으면 제출 직전까지 확인한 뒤 `미검증`으로 기록하세요.

테스트 계정이나 역할별 데이터가 없으면 결과를 추측하지 말고 필요한 계정·상태를 명시하세요.

로컬 실행에 따라 생성되는 `.next` 같은 gitignore 대상 빌드 산출물과 저장소 밖 임시 브라우저 프로필·비식별 캡처는 허용합니다. 점검 종료 후 임시 자산을 정리하고, 추적 파일이 변경되지 않았는지 확인하세요.

## 6. 필수 사용자 시나리오

### A. 첫 방문과 로그인

- 첫 화면에서 서비스의 용도와 가장 중요한 다음 행동을 빠르게 이해할 수 있는지. “5초 내 발견”은 실제 사용자 연구 결과가 아니라 감사자가 수행하는 휴리스틱 대리 평가로만 기록하세요.
- 최신 공지와 다음 일정이 명확히 보이는지
- 로그인 진입점을 쉽게 찾을 수 있는지
- 전화번호·이메일·Google·Kakao 로그인 방식이 혼란 없이 구분되는지
- 로그인 오류가 원인과 다음 행동을 설명하는지
- 공유받은 `/events/[date]` 주소에서 로그인한 뒤 원래 일정과 미완료 행동으로 복귀하는지
- 승인 대기 사용자가 제한 이유와 다음 행동을 이해할 수 있는지
- 초기 로그인 및 비밀번호 변경 흐름이 명확한지
- 현재 화면·코드·README의 가입·회원 승인·운영진 계정 준비 흐름이 서로 일치하는지 먼저 확인하고, 특정 흐름을 제품 요구사항으로 임의 가정하지 않는지

### B. 다음 일정 확인과 참석 응답

- 홈에서 다음 일정, 시간, 장소, 정원, 참석 현황을 빠르게 파악할 수 있는지
- 네이버 지도 연결이 명확하고 안전하게 동작하는지
- 참석·불참·응답 변경 또는 취소 방법을 이해할 수 있는지
- 홈, 일정 목록, 일정 상세의 RSVP 상태와 행동이 일관적인지
- 저장 중 중복 입력이 방지되고 성공 여부가 명확히 표시되는지
- 정원 임박, 일정 없음, 지난 일정 등의 상태가 오인되지 않는지

### C. 일정 탐색과 상세 정보

- 월간 달력에서 일정이 있는 날짜를 쉽게 발견할 수 있는지
- 날짜 선택 후 해당 일정 요약으로 자연스럽게 이동하는지
- 일정 상세에서 참석 명단, 내 팀, 팀 편성, 경기 결과, 득점, MOM 정보를 빠르게 찾을 수 있는지
- 예정 일정과 지난 일정의 행동이 명확히 구분되는지
- MOM 투표 가능·불가능 이유와 재투표 가능 여부를 이해할 수 있는지
- 상세 화면에서 일정 목록으로 돌아갔을 때 문맥이 유지되는지

### D. 회비

- 일반회원이 자신의 납부·미납 상태와 산정 기준을 빠르게 이해할 수 있는지
- 금액, 대상 월, 관련 일정 등의 관계가 명확한지
- 이상이 있을 때 문의 경로를 쉽게 찾을 수 있는지
- 운영진이 전체 현황과 미납자를 빠르게 구분할 수 있는지
- 개인정보와 금액 정보가 역할에 맞게 노출되는지

### E. 공지·회원·랭킹

- 최신 공지와 고정 공지를 빠르게 구분할 수 있는지
- 긴 공지에서도 제목·본문·날짜의 위계가 유지되는지
- 회원 목록에서 필요한 사람을 쉽게 찾을 수 있는지
- 득점·활동·MOM 순위의 기준을 사용자가 이해할 수 있는지
- 큰 표가 모바일과 200% 확대에서 읽고 탐색 가능한지

### F. 선거·투표·설문

- 진행 중, 마감, 참여 완료, 비밀 투표, 마감 시각이 즉시 구분되는지
- 필수 문항과 선택 문항을 명확히 이해할 수 있는지
- 필수 복수선택 문항이 빈 제출을 실제로 막는지
- 긴 답변을 작성한 뒤 닫기, Escape, 뒤로가기, 네트워크 실패가 발생해도 입력이 보존되는지
- 제출 중·성공·실패·중복 제출 상태가 분명한지
- 결과 공개가 설정된 마감 항목에서 실제 결과 확인 경로가 있는지

### G. 사용자 의견

- 의견 분류, 제목, 내용, 익명 여부를 쉽게 입력할 수 있는지
- 익명이 앱 내부에서 의미하는 범위를 정확히 설명하는지
- 시스템 제보가 GitHub에 공개될 수 있다는 점과 공개되는 정보가 제출 전에 명확한지
- 내부 접수 성공과 GitHub 연결 실패를 서로 다른 상태로 전달하는지
- 외부 연결 실패 후 재시도 동작과 결과가 명확한지
- 작성한 의견의 처리 상태와 운영진 답변을 쉽게 확인할 수 있는지

### H. 운영진 과업

안전한 테스트 환경이 있을 때만 실제 저장까지 확인하세요.

- 회원 승인·편집·비활성화
- 월 회비 일괄 등록
- 공지·장소·일정 등록과 편집
- 현장 출석 체크
- 용병 관리
- 팀 편성·재편성
- 경기·득점 기록
- 의견 답변
- 선거·투표·설문 관리
- 역할 및 권한 변경

반복 입력량, 기본값, 일괄 처리, 중간 저장, 잘못된 대상 선택 방지, 되돌리기 어려운 작업의 확인 문구를 중점 점검하세요.

## 7. 사용성 점검 기준

### 탐색성과 정보 위계

- 첫 화면에서 가장 중요한 행동이 무엇인지
- 주 메뉴 8개에서 자주 쓰는 일정·공지·회비를 빠르게 찾을 수 있는지
- 현재 위치가 메뉴와 화면 제목에서 일관되게 표시되는지
- 주요 행동, 보조 행동, 위험 행동의 시각적 우선순위가 적절한지
- 필요한 클릭·탭·스크롤 횟수
- 사용자가 이전 화면 정보를 기억해야만 현재 행동을 수행할 수 있는지
- 한 결정 지점에 너무 많은 선택지나 동등한 강조가 있는지

### 상태 가시성과 복구

모든 변경 행동에 대해 확인하세요.

- 실행 전 결과를 예측할 수 있는가
- 실행 중임을 알 수 있는가
- 중복 실행이 방지되는가
- 성공 후 실제 반영 상태가 보이는가
- 실패 원인과 재시도 방법을 알 수 있는가
- 실패 후 입력이 보존되는가
- 부분 성공과 전체 성공이 구분되는가
- 삭제·공개 게시·권한 변경 등의 대상과 영향을 확인할 수 있는가

로딩, 오류, 빈 결과, 권한 제한, 정상 데이터를 서로 오인할 가능성도 확인하세요.

### 폼 편의성

- 명시적인 라벨, 도움말, 예시, 필수 표시
- 입력 형식, 자동완성, 스마트 기본값
- 전화번호·날짜·시간·숫자 입력 시 적절한 모바일 키보드
- 첫 오류로의 포커스와 스크롤
- 오류 메시지의 구체성과 해결 방법
- 긴 폼의 단계 구분과 진행 상태
- 닫기·뒤로가기·네트워크 실패 시 입력 보존

### 모바일·반응형

최소 다음 환경에서 실제 렌더링하세요.

- 320px, 360px, 390px 모바일 세로
- 모바일 가로모드
- 768px 태블릿
- 1024px 및 1440px 데스크톱
- 브라우저 200% 확대

확인할 항목:

- 햄버거 메뉴 열기·닫기와 섹션 이동
- 한 손 사용 시 핵심 행동의 접근성. 이는 감사자의 휴리스틱 대리 평가이며 실제 사용자 관찰로 표현하지 마세요.
- 프로젝트 사용성 목표인 최소 44×44px 터치 영역. 이를 WCAG 2.2 AA의 일률적인 최소 판정 기준이나 법적 적합성 기준으로 표현하지 마세요.
- 전체 페이지의 의도하지 않은 가로 스크롤
- 달력·표의 의도된 내부 스크롤
- 모달과 긴 운영 폼의 내부 스크롤
- 긴 한국어 이름·공지·장소·문항의 줄바꿈
- 고정 헤더가 제목·포커스·오류를 가리지 않는지

### 접근성

자동 검사만으로 통과 판정하지 마세요.

- 키보드만으로 메뉴, 로그인, RSVP, 설문, 모달, 표, 운영 편집기를 조작
- 포커스 순서와 가시성
- 모달 포커스 트랩, Escape, 닫은 뒤 원래 위치 복귀
- 접근 가능한 이름과 폼 라벨
- 헤딩과 랜드마크 구조
- 로딩·성공·오류의 라이브 리전 알림
- 색상 외의 상태 단서
- WCAG AA 명암
- 200% 확대 사용성
- `prefers-reduced-motion` 대응

실제 스크린리더를 사용하지 않았다면 “스크린리더 검증 완료”라고 표현하지 마세요.

## 8. 우선 검증할 가설

다음은 확정 결함이 아니라 반드시 재현해야 할 후보입니다.

- 공유 일정 URL에서 로그인 후 홈으로 이동해 원래 행동 문맥을 잃는가
- 홈·목록·상세의 RSVP 선택지와 변경 방법이 서로 다른가
- 참석 결정 전에 정원·명단·팀 정보를 충분히 확인할 수 있는가
- 필수 복수선택 설문을 빈 상태로 제출할 수 있는가
- 설문 작성 중 배경 클릭이나 Escape로 입력이 유실되는가
- 결과 공개가 설정된 마감 투표의 결과를 실제로 볼 수 있는가
- 참여 데이터 로드 실패가 “항목 없음”으로 표시되는가
- 일부 데이터 요청 실패가 빈 상태나 정상 상태로 오인되는가
- GitHub 연결 실패가 성공 알림처럼 보이는가
- 익명·비익명 시스템 제보의 공개 범위 설명과 실제 동작이 일치하는가
- 모바일 달력과 팀·경기 편집기가 실제 터치 환경에서 사용 가능한가
- 제한된 권한의 운영진이 잠긴 기능의 이유를 이해할 수 있는가

재현되지 않은 가설은 결함으로 보고하지 마세요.

## 9. 증거와 오탐 방지

각 발견에 아래 확신도를 표시하세요.

- `C3 확인`: 안전한 격리 환경에서 현재 HEAD의 종단간 과업을 재현했고 단계와 비식별 증거가 있음
- `C2 강한 근거`: 과업 일부를 브라우저에서 재현했고 현재 코드 근거가 함께 일치하지만 종단간 쓰기 결과는 확인하지 못함
- `C1 가설`: 정적 코드에서만 의심되며 실행 검증 필요
- `C0 추측`: 보고서에서 제외

각 결함에는 반드시 다음이 포함되어야 합니다.

- 현재 SHA
- URL 또는 화면
- 사용자 역할과 계정 상태
- 필요한 사전 데이터
- 브라우저와 뷰포트
- 정확한 재현 단계
- 기대 결과와 실제 결과
- 사용자에게 미치는 영향
- 개인정보를 포함하지 않은 화면 캡처, PII 없는 DOM 측정·행동 로그 또는 코드 경로
- 구체적인 개선안
- 수정 후 확인할 회귀 기준

주의 사항:

- 코드만 보고 반응형·포커스·명암 결함을 확정하지 마세요.
- 실제 사용자 인터뷰, 감사자의 브라우저 관찰, 코드 기반 추론을 구분하세요.
- 동일 원인의 여러 증상은 하나로 묶고 영향 화면을 열거하세요.
- 개인정보 보호에 따른 정보 제한을 결함으로 오인하지 마세요.
- 제품이 약속하지 않은 신규 기능은 `결함`이 아닌 `개선 기회`로 분리하세요.
- 다크 모드는 별도 요구 근거가 없으면 결함으로 보고하지 마세요.

## 10. 심각도와 우선순위

심각도:

- `S0 Blocker`: 핵심 과업 불가, 중대한 오정보, 복구 불가 입력·데이터 유실, 의도하지 않은 공개, 주요 보조기술 사용자의 완전 차단
- `S1 High`: 핵심 과업의 반복 실패·이탈, 결과 불확실, 모바일 핵심 화면 붕괴, 위험 행동의 중대한 오인
- `S2 Medium`: 우회 가능한 반복 마찰, 탐색성·위계·피드백 문제
- `S3 Low`: 제한적인 가독성·일관성·마감 문제

우선순위는 심각도와 별도로 `Now / Next / Later`로 표시하세요.

빈도, 영향을 받는 사용자 수, 시간 민감도, 되돌릴 수 없음, 확신도를 근거로 결정하세요. 구현 난이도가 높다는 이유로 심각도를 낮추지 마세요. `C1` 항목에는 잠정 심각도만 부여하세요.

## 11. 최종 산출물

다음 순서로 한국어 보고서를 작성하세요.

1. 10줄 이내 총평
2. 가장 치명적인 사용자 마찰 최대 5개. 실제 발견이 적으면 개수를 채우지 마세요.
3. 잘 작동하는 경험 최대 3개. 확인된 항목이 없으면 `확인된 항목 없음`으로 기록하세요.
4. 모든 직교 조합이 아니라 위험 기반 pairwise 커버리지를 사용한 검증 표

   `시나리오 | 라우트 | 역할 | 데이터 상태 | 뷰포트 | 결과 | 증거`

   실제 확인한 조합만 기록하고 역할·상태별 대표 조합 및 제외 근거를 별도로 요약하세요.
5. 핵심 과업별 `완료 / 문제 발견 / 미검증` 결과
6. Nielsen 사용성 휴리스틱 10개를 각 항목별로 평가한 표. `0=사용 불가 수준`, `1=심각`, `2=중대한 마찰`, `3=대체로 양호`, `4=매우 우수`로 정의하고 각 점수의 관찰 근거를 작성하세요. 오해를 부르는 합산 총점은 만들지 마세요.
7. 발견 항목 표

   `ID | 심각도 | 우선순위 | 확신도 | 과업 | 역할·상태 | 기기 | 재현 단계 | 기대/실제 | 사용자 영향 | 증거 | 권고 | 회귀 기준`

8. S0·S1 항목의 상세 설명과 캡처
9. 정상 통과한 항목
10. 미검증 범위와 추가로 필요한 계정·데이터
11. 결함과 분리된 개선 기회
12. 중복 제거된 실행 순서

실행 순서는 다음처럼 정리하세요.

- `Now`: 최대 5건
- `Next`
- `Later`

이번 단계에서는 문제를 수정하지 말고, 전수점검 보고서만 제출하세요. 몇 가지 문제를 발견한 뒤 중단하지 말고 모든 주요 라우트와 핵심 시나리오를 위험 기반 대표 조합으로 확인하거나 명시적으로 `미검증`으로 표시해야 완료입니다.
