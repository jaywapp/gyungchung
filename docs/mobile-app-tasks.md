## 계획 기준과 범위

최신 웹의 매치 콘솔 디자인을 사용하는 Expo/React Native 앱을 `mobile/`에 만든다. iOS와 Android에 동일한 회원 기능을 제공하며, 기존 웹과 Supabase를 함께 사용한다. 이 문서는 개발 작업을 발주·검토할 수 있는 수준의 실행 계획이다. 화면별 출시 범위의 최종 결정은 M01에서 기록한다.

| 범위 | 계획 기준안 |
| --- | --- |
| 첫 기술 검증 | 전화번호 로그인, 초기 비밀번호 변경, 세션 복원, 다섯 탭, 테마, 다음 경기·일정 상세·참석 응답 |
| 1차 출시 추천 | 기본 프로필, 공지, 본인 회비 조회, 포지션별 회원, 시즌 랭킹, 기본 투표·설문, 업데이트·개인정보·지원 안내 |
| 조건부 작업 | 공개 의견·제보, MOM·선거·비밀투표, 운영자 편집·출석·우승 기록, 방문자 모션 |
| 후속 검토 | 푸시 알림, 앱 내 결제 등 별도 기획이 필요한 기능 |

공개 의견과 운영자 기능을 포함하는 경우 해당 작업의 완료를 출시 게이트에 추가한다. 제외하는 기능은 앱의 메뉴·홈 모듈·심사 자료에서도 제외한다. 현재 웹에서 완료된 기능은 모바일 구현 완료로 간주하지 않는다.

## 작업별 산출물과 구현 범위

### M01·M02 — 개발 시작 조건

산출물은 분석 문서 D01~D08의 결정 기록과 `docs/mobile-app-environments.md`이다. 환경 문서에는 운영·시험·심사의 구분, 테스트 계정 역할, 가상 데이터 종류, 초기화 절차와 책임자를 기록하며 실제 비밀번호·토큰·프로젝트 비밀은 넣지 않는다.

활동 회원·승인 대기·비활동·미연결·초기 비밀번호 변경·제한된 운영 권한 계정을 준비한다. 정상/빈 일정·정원 없음/초과·본인 회비·공동 순위·진행/마감 참여 데이터를 준비한다. 심사 계정의 접근 경계를 결정하고 서버 조회로 실제 회원 정보가 노출되지 않음을 검증한다. 데이터 초기화는 격리 환경에서만 실행한다.

### M03 — 저장소와 빌드

변경 후보는 루트 `package.json`·잠금 파일·`tsconfig.json`·ESLint 설정, `mobile/package.json`·`app.config.ts`·`eas.json`이다. 착수 시점의 Expo 지원 버전을 확인해 고정하고, React 및 네이티브 모듈 중복과 Metro/EAS의 workspace 해석을 확인한다.

공용화는 기존 순수 로직의 import 경계를 조사한 뒤 최소 범위로 결정한다. `packages/domain/`은 양쪽 소비자가 생긴 로직만 추출하며, 추출하지 않는 경우 그 이유를 기록한다. 웹 CSS·DOM·Supabase 브라우저 클라이언트를 모바일로 직접 가져오지 않는다.

완료 증거는 깨끗한 설치에서의 웹 검사·빌드, 두 OS의 설치 가능한 시험 빌드 ID와 실행 결과, 환경별 앱 설정과 서명 책임자 기록이다. iOS 서명 계정이나 실기기가 없으면 해당 검증은 대기 상태로 기록한다.

### M04 — 화면 기반과 디자인

산출물은 `mobile/src/theme/`·`ui/`, 탐색 레이아웃 및 글꼴·브랜드 자산이다. 현재 A안을 기준으로 모바일 적용 샘플 3종을 먼저 제시하고 선택 결과를 기록한다. 실제 UI 작업에서 저장소 규칙의 디자인 스킬을 적용한다.

공통 요소는 버튼·배지·입력·카드·확인 대화상자·상태 안내·로딩·빈 상태·오류/재시도다. 라이트·다크·시스템 테마, 글꼴 로딩, 글자 확대와 터치 영역을 검증한다. 홈·일정·회원·랭킹·더보기 탭과 상세 스택, 키보드, safe area, 시스템 뒤로가기를 연결한다.

### M05 — 인증과 계정 경계

산출물은 `mobile/src/services/`의 모바일 Supabase 클라이언트·인증 서비스, `storage/`의 세션 어댑터, 로그인·초기 비밀번호 변경·계정 안내 화면이다.

전화번호 정규화와 비밀번호 로그인, 세션 저장·자동 갱신, 앱 활성화 복귀, 로그아웃과 계정 전환을 처리한다. 비밀번호 변경의 기존 서버 경로와 권한 계약을 확인한다. 프로필 미연결·대기·비활동·초기 비밀번호 변경 상태를 구분하고 딥링크 목적지를 인증 후 복원한다.

직접 API 요청으로 권한 제한을 확인한다. 캐시와 초안은 계정별로 분리하며 세션 종료 후 회원 정보가 화면·기기 캐시에 남지 않도록 처리한다. 앱에는 공개 가능한 키만 포함한다.

### M06 — 첫 번째 사용 가능한 흐름

산출물은 `mobile/src/features/home/`·`events/`, 일정·참석 데이터 서비스, 지도 및 상세 이동이다. 기존 날짜·정원·RSVP 규칙을 모바일에서도 동일하게 사용한다.

다음 경기와 필요한 명단을 조회하고 매치 콘솔에서 참석/불참/취소를 저장한다. 진행 중 중복 요청을 막고 실패 시 이전 응답으로 복구한다. 응답 마감·정원 미설정/초과·권한 오류를 처리한다. 웹 `YYYYMMDD` 일정 링크, 잘못된 날짜, 로그인 후 복귀를 검증한다.

서울 시간으로 날짜·요일·시각·마감을 표시하고 재연결·앱 복귀 시 서버 상태를 갱신한다. 초기 응답 시간·요청 수·전송량을 측정해 이후 기능에서 비교할 기준을 남긴다. 기존 웹의 일괄 조회 구조를 이 작업에서 변경하지 않는다.

### M07 — 회원 조회 기능

산출물은 공지·회비·프로필·회원·랭킹 화면과 홈 모듈 연결이다. 공지는 고정·최신 항목을, 회비는 본인 납부·미납과 기준을 표시한다. 프로필에서 기본 정보·비밀번호 변경·로그아웃으로 이동한다.

회원 목록은 기존 directory RPC, 포지션 필터·개수·정렬·직책·본인 표시를 사용한다. 랭킹은 연도 선택, 상위 5행, 공동 순위, 테스트 계정 제외와 MVP 집계 의미를 유지한다. 홈은 공지 3건·회비 요약·득점/MVP 3행 등 기존 모듈 계약에 맞춘다.

필터·계정·연도 변경과 서버 권한 제한, 목록 빈 상태·실패 재시도를 검증한다. 조회 기능이 완성된 뒤 홈에서 목적지까지 왕복하는 흐름을 확인한다.

### M08 — 기본 참여

산출물은 참여 목록·폼·본인 응답·허용된 결과 화면, 계정별 초안 저장 어댑터다. 기존 입력 검증과 제출 RPC의 계약을 확인하고 필수 문항·중복 제출·마감 직전 서버 거절을 처리한다.

이동·재시작 후 일반 폼 초안을 복원하고 제출 성공이나 로그아웃 시 정리한다. 선거·비밀투표가 출시 범위에 포함되면 M10 검증을 추가하고 비밀 응답의 로컬 저장·개별 조회 제한을 유지한다. 클라이언트 시간에만 의존하여 제출 가능 여부를 결정하지 않는다.

### M09·M10 — 선택된 확장만 구현

의견 기능은 비공개 원본·회원 공개 목록·GitHub 공개의 대상과 동의를 분리한다. 공개 목록에는 필터·신고·처리·차단·지원 흐름을 갖추고, 외부 공개 실패에도 원본 접수 상태를 유지한다.

운영자 기능은 실제 권한별 화면과 확인 절차, 부분 실패·재시도·저장 이후 갱신을 작업 단위로 추가한다. MOM·선거는 기존 출석·자기 투표 금지·비밀 응답 규칙을 검증한다. 모션은 움직임 줄이기·백그라운드 정지·로그인 진입 방해 여부를 확인한다.

범위가 확정되면 하위 작업의 owner·model·effort·depends_on·parallel_group·verification·status를 추가하고 M11·M13의 완료 조건을 함께 갱신한다.

### M11 — 시연 환경과 심사 자료

산출물은 제출 빌드에서 접근할 수 있는 전체 시연 데이터, 앱 내 개인정보·지원·계정 처리 안내, 앱 버전별 업데이트 노트, `docs/mobile-app-review-guide.md`이다.

일정·회비·랭킹·참여 및 선택된 기능을 심사 계정으로 끝까지 실행한다. 정책 URL, 스크린샷, 설명, 개인정보 수집 답변, 필요한 SDK·OS 권한과 시연 방식의 설명을 준비한다. 심사용 비밀번호는 문서나 Git에 보관하지 않고 제출 시스템의 지정 필드에서 관리한다.

### M12 — Android 설치와 업데이트

산출물은 고정 앱 ID·서명으로 만든 APK, 버전·SHA-256·배포 기록, 팀용 다운로드 및 설치 안내다. 같은 서명과 증가한 버전으로 실제 기기에서 기존 앱 위에 업데이트한다.

키 보관·복구 책임, 다운로드 접근 방식, 구버전 안내를 기록하고 개발자 인증 적용 조건을 출시 시점에 확인한다. 서명이 다른 APK를 업데이트 경로로 안내하지 않는다. 앱/서버 호환 문제에 대비한 중단·수정 빌드 배포 절차를 정한다.

### M13·M14 — 검증과 팀 배포

산출물은 `docs/mobile-app-qa-report.md`, TestFlight 검증 기록, 심사 결과와 미등록 배포 승인, 팀 설치 안내·운영 인계다. 아래 매트릭스의 필수 항목을 실제 출시 후보 빌드에서 검증한다.

iOS는 TestFlight 시험 후 완성된 버전을 App Review에 제출하고 미등록 배포 요청을 진행한다. 두 승인을 각각 확인한다. 심사 수정이 발생하면 변경 기능과 관련 회귀 검사, 심사 자료를 다시 검증한다. Android·iOS의 실제 팀원 설치와 문의·오류 수집 담당자를 확인한 뒤 완료 처리한다.

## 의존 관계와 병렬 진행

개발의 주 경로는 `M01 → M03 → (M04 + M05) → M06 → (M07 + M08) → M11 → M13 → M14`이다. `M02(test_ready)`는 M05에, `M12`는 M13에 합류한다. 선택된 M09·M10은 출시 자료와 최종 QA 전에 합류한다.

| 병렬 구간 | 함께 진행 가능한 일 | 순차 처리할 공유 변경 |
| --- | --- | --- |
| 착수 | 범위·기기·계정 결정과 격리 환경·개인정보 초안 | 공통 환경·스키마와 계정 초기화 |
| 기반 | 테마·탐색과 인증·세션 | 루트 workspace·잠금 파일·라우트 레이아웃·공유 저장소 인터페이스 |

병렬 작업은 파일 소유권과 인터페이스를 먼저 정한다. 공유 변경은 한 담당자가 통합하고 다른 작업은 해당 커밋을 기준으로 진행한다.

## PR과 작업 인계

PR은 빌드 가능한 경계로 나눈다. 권장 순서는 기반(M03), UI 기반(M04), 인증(M05), 핵심 흐름(M06), 회원 조회(M07), 참여(M08), 선택 확장, 심사 안내(M11), 배포 설정(M12), 검증 수정(M13)이다. 범위가 크면 같은 작업 ID 아래 기능별 PR로 나눈다.

각 PR에는 작업 ID, 산출물, 확인한 기기·역할, 테스트 결과와 미검증 항목을 기록한다. 웹 및 설치된 이전 앱에 영향을 주는 계약 변경은 명시한다. 사용자에게 보이는 변경에는 저장소 규칙대로 업데이트 노트를 추가한다. 테스트 계정 자격 증명과 서명 키는 첨부하지 않는다.

완료 인계는 `commit/PR → 빌드 ID·버전 → 검증 결과 → 남은 결정·알려진 제한 → 다음 작업` 순으로 기록한다. `planned → in_progress → verified → done`으로 상태를 관리하고, `done`은 산출물과 검증 증거가 모두 있을 때만 쓴다.
